## Existing integration and smallest option

Inspected `worker.ts` HTTP handler returns only `AI Agent Radar worker ready` and cannot invoke monitoring; scheduled execution alone calls the monitoring handler. `notificationOrchestrator.ts` prepares eligible/deduplicated items, checks notification history twice, selects at most four, formats content, calls `freezeDelivery`, reserves a daily ledger record and dispatches/reconciles through that authority. `emailDeliveryLedger.ts` freezes exact subject/text/HTML, sender, aliases and SHA-256; recovery restores the same bytes. `discoveryPriority.ts` already exports deterministic classifyDiscoveryTopics with ai_ml, it_infrastructure, programming, developer_tools_workflow. AI coding agents/Codex/Claude Code and developer tools are already represented; no taxonomy expansion is justified for MVP.

Option A, narrowly scoped existing Worker routes, avoids a second deployment/binding/signing-key synchronization problem and reuses D1 and existing delivery authority. Recommend A, explicitly subject to human approval of the changed HTTP/security boundary. Option B, dedicated feedback Worker, offers clearer deployment separation but duplicates configuration, shares database authority anyway and adds operational failure modes. Use B only if human security review requires isolation. Neither option permits HTTP monitoring or provider access.

## Product contract and capabilities

All actual story cards in newly prepared emails, including raw degraded highlights, receive two clear HTML and text links: Relevant and Not relevant. Status-only mail has no story/vote controls. Raw stories can be rated but have no inferred preference topics; analyzed stories use existing deterministic taxonomy. Do not create fake analyses or discoveries for raw highlights.

Each link names one server-bound delivery/slot and intended rating, never a client-supplied article URL. The confirmation page displays a bounded escaped title and chosen rating, then an explicit submit button. GET/HEAD have zero feedback writes and no state-creating token issuance in D1. POST alone commits. Link scanners, previews and repeated GET/HEAD cannot vote. This is two-step confirmation, not true single-click recording.

Proposed capability: compact canonical base64url payload plus HMAC-SHA-256 using Worker Web Crypto. Fixed field order and exact keys: version=1, key ID, delivery key, slot 1..4, story SHA-256, rating enum, issuedAt, expiresAt. No email address, recipient ID, arbitrary URL or title in token. Maximum token 1,024 bytes; total request URL ≤2,048 bytes. Fixed configured audience/purpose is included in signing input (e.g. radar-feedback-v1 + approved origin); never derive it from untrusted Host. Verify MAC via crypto.subtle.verify, reject noncanonical encoding, extra fields, wrong audience/version/key, invalid dates/rating/slot and every mismatch with the stored immutable delivery binding. No secret returned to browser.

issuedAt is the immutable delivery scheduledAt; expiresAt is issuedAt+30 days. Bounded expiry permits reading older email and corrections while limiting exposure. At most active and one retiring key are accepted; retain retiring verification key until all issued links expire (30 days plus existing delivery recovery window). Never rotate keys during an unresolved preparation/recovery conflict without evaluating frozen links. Missing keys/config fail closed for feedback. No runtime key generation or secret provisioning is part of this design task.

Forwarded email grants the bearer capability to whoever receives it; there is no recipient authentication in MVP. It is not proof of the recipient's identity. An attacker/scanner that deliberately completes the valid POST can vote; GET-safety does not prevent intentional form execution. Communicate this limitation on the confirmation page and runbook.

## Routes, request bounds and browser security

Propose exactly GET/HEAD `/feedback` with one token parameter and POST `/feedback/confirm`. Preserve existing health response elsewhere; reject unsupported methods on feedback routes with fixed 405/Allow. No redirect destination or callback URL is accepted. No handler may call monitoring, discovery, Gemini, Brave or Resend. Existing scheduled route remains independent.

Require HTTPS and configured exact feedback origin. GET validates token, loads binding and delivery acceptance, renders a ≤16 KiB HTML page. HEAD returns equivalent safe headers without body or writes. Invalid/expired/unaccepted delivery returns bounded generic explanation; never leak whether unrelated story/recipient exists. D1 unavailable returns safe 503 with no write. Do not redirect externally or include third-party resources.

Page contains a stateless signed confirmation nonce (purpose-separated HMAC) bound to capability digest, current vote revision and a 10-minute expiry. No D1 mutation is required to render it. POST requires the original capability, signed confirmation nonce, intended rating and expected current revision; nothing else. Enforce application/x-www-form-urlencoded, strict field/key cardinality, streaming body ≤4 KiB and 5-second body-read timeout, including absent/misleading Content-Length. No JSONP, CORS, query mutation, arbitrary methods or auto-submit script. Require Origin to equal the approved origin; fail closed if missing/null/cross-origin. A conventional same-origin HTML form provides the confirmation; JavaScript is unnecessary.

Responses use Cache-Control: no-store, Referrer-Policy: strict-origin, X-Content-Type-Options: nosniff and restrictive CSP (default-src 'none'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'; only fixed local/inline-nonce styling if required). No cookies or tracking. Never interpolate titles without escaping; bound UTF-8 title to 256 bytes without splitting code points. Do not include token/nonce in application logs or thrown errors. Before release, independently verify Cloudflare request logging and error reporting do not retain query tokens; if that cannot be established, redesign token transport/redaction before activation. No promise that application redaction controls platform logging.

No unbounded token/store lookup, feedback export or analytics endpoints. Cryptographic checks precede D1 reads. Invalid traffic is bounded per request; public traffic exhaustion remains a residual operational risk. Review existing platform protections before activation; do not silently add paid WAF/rate-limit resources.

## D1 data model and exact delivery association

Inspected migration directory contains 0001 through 0010 (0004 intentionally excluded from production selection). Next available candidate is `0011_email_feedback.sql`, proposed only; recheck immediately before Builder creation. `wrangler.jsonc` has an explicit migration allowlist ending at 0010: 0011 is NOT automatically selected. A future approved migration change must explicitly extend the allowlist, prove selection/history/repeat/no-0004 with a production-shaped isolated local fixture and obtain separate production application approval.

Three small tables, no profile table or new persistence service:

1. `email_feedback_stories`: composite primary key (delivery_key, slot), FK to email_deliveries; immutable payload_sha256, discovery_key (SHA-256 of canonical normalized URL), bounded display_title, kind analyzed/raw, topic_version=1, topics_json containing distinct allowlisted topics in taxonomy order (0..4), issued_at, expires_at, key_id, two fixed capability digests (Relevant/Not relevant), created_at. This is the original delivered-card association, including raw items without a StoredDiscovery row. No arbitrary client URL or duplicate article body is stored. The full original frozen payload/aliases remain the existing authority. One record per actual final card, maximum four per delivery.
2. `email_feedback_votes`: primary key (delivery_key, slot), FK to binding; current rating enum, revision 1..10, created_at/updated_at (DB UTC), digest reference of confirmed capability. Exactly one current vote per delivered story.
3. `email_feedback_events`: primary key (delivery_key, slot, revision); append-only within retention: previous rating (nullable first), new rating, DB UTC recorded_at and capability digest. At most ten distinct changes per story/link lifetime. An ordinary duplicate does not append an event or increase revision. No browser/IP/user-agent/referrer or email data.

Use CHECK/FK/unique constraints and an atomic D1 transaction/batch for compare-and-set current vote plus its matching audit event. Bind all SQL parameters. Independent Workerd tests must prove the actual transaction behavior, concurrent change conflicts, response loss and restart semantics. Do not use an unsafe SELECT-then-UPDATE without revision condition. A DB-side transition/trigger or conditional batch must make current vote and one event inseparable; do not rely on statement affected-row metadata without testing D1 semantics.

Before recording a vote, require the exact email_deliveries row to be accepted and binding.payload_sha256 to equal its immutable payload hash. Pending/ambiguous/failed rows are not proof of delivered content and cannot vote; tell an actual recipient whose acceptance record is still ambiguous to retry later. Notification reconciliation does not issue feedback or send another email. The binding is never re-associated with another URL/title/slot after reserve.

## Frozen payload boundary and one explicit approval conflict

New preparation only, after eligibility/history/dedupe/selection and after checking for an existing recoverable daily record: derive all card identities/topics/capabilities deterministically from the delivery identity, final cards and approved signing key; format HTML/text with both links; freeze exact bytes once. Atomically reserve the ledger and matching story bindings before any dispatch. Extend the existing D1 reserve boundary narrowly so either the matching frozen payload plus all ≤4 bindings exist or neither does; conditional binding creation must match the winning ledger payload hash. Concurrent preparation losing a reservation must use the winning stored payload and bindings, never mix versions. Existing records without feedback bindings remain valid, recoverable and unchanged.

Recovery NEVER re-renders links, re-signs tokens, recalculates expiry, re-ranks stories or changes frozen bytes/key. New keys or preference changes cannot alter a pending payload. Feedback reads/writes never invoke an email send. Any preparation metadata failure blocks that new preparation safely; do not silently send newly prepared story emails without required controls. Existing historical frozen records without links recover under existing rules; do not backfill email content.

**Human decision required:** the brief prohibits storing raw signed tokens, while also requiring signed links in immutable frozen HTML/text. Those two requirements cannot both hold literally across the existing email ledger. Recommended minimal exception: permit tokens only inside the already-required frozen provider payload, with the existing restricted retention/access controls; feedback tables and all logs store digests only. No extra HTML copy or new raw-token column. This exception is NOT approved by this document. If the human requires zero persisted signed tokens anywhere, stop feedback implementation and revisit capability transport/frozen-payload design explicitly; do not weaken idempotency or evade the prohibition by renaming a token. This does not block the independent Brave design handoff.

## Idempotence, corrections and retention

Identical current rating returns already-recorded without revision/event increment even on retried POST. A differing rating requires a fresh confirmation nonce bound to the currently observed revision. CAS conflict returns 409 and asks the user to reopen confirmation; stale confirmations cannot revert a newer vote. First insert is revision 1 with expected revision 0. A valid different choice creates revision+1 and one event atomically. Maximum ten revisions within 30-day link lifetime; at limit return clear bounded explanation, no silent overwrite. This provides a small audit trail and bounds bearer abuse. Signed old pages cannot replay earlier corrections after a newer revision.

Preference query uses current votes only, never event counts. Window is last 90 days by immutable delivery scheduled date, not updated_at: changing an old vote does not rejuvenate it. Bound query to latest 400 distinct discovery identities with deterministic delivery_date/slot/key ordering; use latest delivered instance per discovery_key before accumulating, though notification dedupe should normally prevent repeats. A digest may contribute at most four stories. At daily delivery rate ≤4, 90 days normally yields ≤360; 400 is bounded headroom.

Retain feedback binding/current vote/audit events for 180 days by immutable delivery date, then delete the feedback records together only; preserve the underlying email ledger and notification history. Historical audit exists within this declared window, not forever. Prune at most 20 expired delivery groups per normal scheduled cycle, transactionally child-first, with no new Cron or endpoint; cleanup failure is bounded and does not alter eligibility/send authority. At the current daily rate this exceeds ingestion. Never prune valid capabilities or extend expiry from votes. Implementation approval must explicitly cover this bounded feedback-only retention policy.

## Deterministic conservative preferences

Use classifyDiscoveryTopics on the final validated analysis at preparation, persist its sorted closed topics once; no model judgment beyond the original existing analysis, no extra LLM call. A story may belong to multiple existing topics; contribute once per topic, once per discovery identity. Raw/unclassified stories have an empty topic list and do not affect preferences. No new category is needed for coding agents or developer tools.

For each topic over the recent bounded window, P/N are positive/negative distinct-story counts. If P+N<5 or abs(P−N)<3: insufficient/mixed, adjustment 0. Otherwise adjustment = 0.5*(P−N)/(P+N), hence within [−0.5,+0.5]. Positive and negative classification follows sign. This needs repeated evidence, limits impact and keeps contradictory feedback near neutral. For a multi-topic story, mean the adjustments across its full topic set (including zero topics), never sum; unknown/no topics score 0. Replacing a vote recomputes contribution; no additive counters drift.

The smallest safe ranking integration is a tie-break, not eligibility or a new selection pool. In `prepareDailyDigest`, after both history checks and before four-item slice, preserve existing fresh/replay/raw lanes and existing relevance ordering; only within same-lane, equal original relevance-score analyzed candidates use preference adjustment descending, then original stable index. Raw candidates keep existing order. Never move an item across normal/fallback/source-trust boundaries, inject unselected Gemini candidates, lower the threshold, re-notify aliases, add a fifth item, override prompt rank across different scores, or rewrite analysis.relevanceScore. This can affect prominence and tied eligible selections; with ≤4 distinct-score fresh selections it may have no effect. That conservative limited effect is intentional MVP, not a promise of strong personalization.

Read the profile once per new preparation, before freezing. Missing/invalid/unavailable profile means neutral ranking with one fixed-category warning; it cannot bypass notification-history/ledger failures or trigger telemetry-degraded content continuity. Existing admitted content and provider budgets remain intact. Feedback store failure cannot become permission to resend. No profile is sent into Gemini prompts or treated as instructions.

Important existing-contract discrepancy: current scheduled Batch/daily preparation can admit lower-score selected stories and raw degraded highlights under its reviewed daily-delivery policy; generic governance still describes threshold/P4 rules. Do not silently replace runtime eligibility during feedback work or claim all sent items meet ≥7. Preference is applied only to already-admitted candidates and cannot create any eligibility exception. Analyst must pin the baseline behavior; reconciling broader threshold policy is a separate human decision, not a feedback implementation change.
