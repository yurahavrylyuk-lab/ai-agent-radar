## Eligibility: all conditions required

1. A scheduled nonempty PreparedBatch actually attempted Gemini, using the existing V2 policy.
2. Exactly three actual dispatches exhausted its current maximum; ordinals 1/2/3, all reviewed `unavailable_503`, all durably `confirmed_zero`, final retry decision `stop/max_attempts`.
3. Read authoritative matching cycle/attempt/usage evidence from D1; verify each attempt's reservation identity and settled status. An in-memory error string, HTTP status alone, or console log is insufficient. Fresh Gemini guard state must have no unresolved reservation, usage_unknown, accounting error, timeout ambiguity or inconsistent evidence. Failure to prove this disables Luna.
4. Time, OpenAI configuration and atomic spending admission all pass.

No fallback after zero/one/two attempts, quota/deadline-shortened retry sequence, 429, other HTTP class, timeout, transport error, ambiguity, accounting/telemetry failure, invalid output, successful response (including valid empty selections), or blocked Gemini preflight. Do not use Luna to repair a successful but uninteresting result. No parallel providers; no later Gemini retry once Luna is considered.

## Timing: preserve the envelope, reserve finalization

Code inspection shows `batchDeadlineStartedAt` is private to Gemini and starts immediately before its first provider interaction; it is not the monitoring-cycle start. Gemini uses a 75,000ms cutoff within its configured 90,000ms envelope. Export/read the same monotonic start through the cycle context rather than restarting a timer for Luna or changing Gemini cutoff/backoff.

Choose **15,000ms** for Luna fetch through complete response body/JSON validation, **5,000ms** accounting allowance, **10,000ms** finalization reserve. Admission requires at least **30,000ms remaining** under BOTH `firstGeminiStart + 90,000` and `cycleStart + 110,000` (monotonic execution start, not scheduled timestamp). Missing start evidence denies admission. Thus Luna starts no later than Gemini-envelope elapsed 60s and cycle elapsed 80s. Preserve the existing 75s Gemini cutoff even though late confirmed-zero exhaustion may leave Luna ineligible.

Recheck immediately before reservation and after durable dispatch intent immediately before fetch. If reserve is lost before fetch, record provable pre-dispatch cancellation; never fetch late. Never reduce finalization reserve to squeeze in a request. Abort includes body reads, not just headers; ignore late completion and cancel the stream. Exact accounting must settle before returning normal analysis. A hung D1 operation is not cancellable merely by racing a promise: bound caller waiting, never let a late reservation result dispatch, and leave any unconfirmed durable row blocking future Luna. The 110s target remains a performance target, not a hard platform kill or guarantee that D1/email cannot stall. No new retry or background recovery.

## Request and validation contract

Official documentation checked on 2026-10-24 confirms [gpt-6-luna](https://developers.openai.com/api/docs/models/gpt-6-luna) supports Responses and low reasoning, with standard short-context input/output pricing of $0.10/$0.50 per million tokens. Account access remains a release prerequisite, not something verified here. [Text generation](https://developers.openai.com/api/docs/guides/text) describes Responses output handling; [reasoning guidance](https://developers.openai.com/api/docs/guides/reasoning) explains reasoning/output budgeting.

One native POST to fixed `https://api.openai.com/v1/responses`, redirects rejected, no SDK auto-retries, tools, retrieval, conversations, previous_response_id, background mode, streaming or provider polling. Pin `model: gpt-6-luna`, `reasoning: {effort: low}`, `store: false`, `stream: false`, `max_output_tokens: 12288`, default standard reasoning mode/service tier. No temperature or unsupported Gemini parameters. Input is the exact already-prepared `batch.prompt` (<=12,288 UTF-8 bytes) and exact submitted candidate identities (<=24); no additional instructions expanding that bound. Use prompt's existing JSON contract with a small provider-side strict JSON shape; no separate business output model.

Bound full response wire body to 128 KiB, fatal UTF-8 decoding, abort/cancel on overflow, and require completed status. Traverse Responses output message/content items for output_text; do not assume a top-level SDK convenience `output_text` exists in REST JSON. Require one unambiguous textual answer, reject refusal/tool calls/incomplete/truncated responses, and enforce shared decoded output cap 24,576 bytes. Reasoning metadata is never treated as story content or logged.

Validate exact nonnegative integer input_tokens/output_tokens/total_tokens, total=input+output, counting reasoning within reported output (not adding it twice). Persist trustworthy usage even if business output is invalid/incomplete. Missing/untrustworthy usage is unknown, never inferred from visible text. Use `parseBatchAnalysis(outputText, samePreparedBatch)` unchanged: exact keys/schema, <=4 unique known IDs, descending scores 1–10, field bounds and application-owned title/URL. No repair call, partial acceptance or generated sources.

Valid Luna selections return as normal analyzed selections, including existing below-7 labels. Valid empty selection is not an outage; retain existing replay/no-selection behavior. Luna failure goes through the existing finalizer with the original full raw pool; eligible analyzed replay may still yield normal mode under current policy. Do not force degraded mode over eligible replay or fabricate a story when no content exists. One shared email-attempt context, max four stories, at most one final email attempt; no claim of exactly-once delivery across acceptance/history ambiguity.

## Durable OpenAI accounting and migration

**New migration required:** proposed `0009_openai_fallback_usage.sql` (verify number still free at implementation). One narrow `openai_fallback_usage` table, no edits to applied Gemini migrations, no dependency on 0004, no generic provider platform. Existing Gemini attempt table is model-constrained and must not store Luna rows.

One row per cycle: immutable cycle_id (unique, references monitoring_cycles), scheduled_at (unique scheduled execution identity), model pinned to gpt-6-luna, DB UTC reserved_at, monotonic accounting_through, input/output reservation caps, request count=1. Mutable state: `reserved | exact | unknown | cancelled_pre_dispatch`; dispatch `not_dispatched | intent | observed`; exact nullable token columns; bounded failure class/HTTP status; persistent budget_anomaly flag; start/end timestamps and duration. The budget anomaly flag cannot be cleared by ordinary runtime transitions and independently blocks admission. CHECK/trigger constraints enforce immutable identity, forward-only dispatch, exact arithmetic, monotonic interval, no fabricated token zeros for unknown, terminal evidence protection and no ordinary deletion. Partial unique index permits only one reserved/unknown row globally. A surviving reserved row is unresolved, even after restart.

Atomic conditional INSERT checks limits and absence of unresolved rows in the same D1 statement, including DB-read Gemini eligibility; unique constraints prevent concurrent/replayed issuance. Return/read exact inserted identity before proceeding. Never separate check and reservation into a race-prone read then unconditional write. Persist `intent` before fetch; confirm its exact identity/state, then final time check and one fetch. In-memory consumed flag plus unique cycle/scheduled identity prevents repeated dispatch after failures. Do not resume a previous intent row or auto-release a lock on elapsed time.

Settlement conditional on exact row identity: `reserved → exact` only with validated usage and confirmed durable write; `reserved → unknown` for dispatched uncertainty. If settlement fails, leave reserved as the durable blocking state. `cancelled_pre_dispatch` is allowed only when the current invocation can prove fetch never ran; zero billable usage then is local non-dispatch evidence, not provider-confirmed zero. A crash near intent remains unresolved. No automatic unknown recovery/expiry/retirement in v1; require separately reviewed evidence-based recovery. HTTP failure without trustworthy usage conservatively becomes unknown, including OpenAI 429/503; do not import Gemini confirmed-zero rules.

OpenAI unresolved state disables future Luna admission, including after restart and across accounting windows. It does not rewrite Gemini's latch or prohibit safe Gemini-primary work on later cycles. Any Gemini uncertainty forbids Luna in that cycle. No other AI fallback exists. Missing table/config/state disables only Luna and preserves primary/degraded delivery.

## Spending guard (proposed, source controlled)

Hard dispatch ceiling one per cycle, plus UTC calendar day/week (Monday)/month requests **1 / 7 / 31**. Reserve **12,288 input + 12,288 output/reasoning = 24,576 tokens** before dispatch; daily/weekly/monthly token budgets **24,576 / 172,032 / 761,856**. Compare current charged usage PLUS full new reservation to each limit atomically. Unresolved rows block independently of counters. Use DB UTC window boundaries and charge a request/its full tokens to every window intersecting [reserved_at, accounting_through], conservatively handling midnight/week/month crossings. Recheck windows before dispatch; cancel before fetch on a rollover rather than carrying an unchecked reservation into a new window.

The reservation is a pessimistic SAFETY/SPENDING BUDGET, not a tokenizer estimate or assertion that UTF-8 bytes equal tokens. The fixed prompt is <=12,288 UTF-8 bytes; only one dispatch/cycle is possible; max_output_tokens=12,288 caps generated output INCLUDING reasoning; independent 1/7/31 request ceilings bound exposure; and exact usage replaces the reservation when safely persisted. No tokenizer dependency or token-count API is needed. This resolves the former tokenizer-substantiation gate by adopting the human-approved budgeting contract, not by claiming a mathematical input-token upper bound.

Validate nonnegative safe-integer input/output usage; require total_tokens to be a safe integer equal to their sum under this adapter's strict response contract. Retain exact values even if above a reservation. If exact usage exceeds either component or total budget, settle actual values with durable budget_anomaly=1, degrade and block later Luna; never clamp usage or silently increase quotas. Thus token admission ceilings are budgets, not a guarantee that a single reported usage cannot exceed them. At supplied standard rates, usage equal to the reserved components costs $0.0073728/attempt or $0.2285568 for 31; this is a budget illustration, not a hard invoice ceiling. Unknown usage remains blocking across windows; request caps and fixed finite payload/output limits provide independent bounded exposure.

### Structured output and output-cap acceptance

Official [Structured Outputs documentation](https://developers.openai.com/api/docs/guides/structured-outputs) and the Luna model page confirm compatibility. Use Responses `text.format = {type: "json_schema", name: "radar_batch_v1", strict: true, schema: ...}`. Schema mirrors the existing envelope: object with required schemaVersion (integer enum [1]) and stories (array maxItems 4); each story requires exactly candidateId, relevanceScore (integer 1–10), category (existing enum), name, summary, whyItMatters, educationalValue, technologies and projectOpportunities. All objects set additionalProperties=false; all prose/IDs are strings; technologies/projectOpportunities are string arrays with maxItems 8/3. Keep schema fixed, not regenerated with source strings. Existing validator remains authoritative for nonempty/UTF-8 limits, rank-specific limits, known/unique IDs, ordering and application-owned title/URL. Schema metadata adds bounded request overhead but does not alter PreparedBatch.prompt; do not treat schema bytes as story input or a reason to raise prompt limits. No schema auto-retry/downgrade on HTTP rejection.

Require response status=completed. Incomplete responses, including incomplete_details.reason=max_output_tokens, never produce analysis even if their text looks valid; retain exact billing if available, otherwise unknown; degrade with no retry. Test representative 24-candidate/12,288-byte prompts and maximum valid four-story output including rich first-story fields, Unicode and reasoning usage within total output 12,288. Fixtures prove adapter/schema/cap handling, not actual model generation reliability. Use reviewed, already-available provider-contract evidence where available; do not fabricate such evidence or make unauthorized provider calls. Natural validation records cap exhaustion separately. If offline or authorized provider-contract evidence demonstrates the cap cannot support the schema reliably, STOP for a bounded amendment; never raise the cap in runtime.


Match current quota configuration pattern: six `OPENAI_{DAILY,WEEKLY,MONTHLY}_{REQUEST,TOKEN}_LIMIT` Worker vars with defaults explicitly supplied in future wrangler config, positive integer validation and source-controlled maximum ceilings above (operators can reduce, cannot silently raise). Pin model/reasoning/output/time constants in `src/config/openaiFallback.ts`; do not allow arbitrary OPENAI_MODEL overrides. Feature-specific optional binding `OPENAI_API_KEY` (do not make it a global startup-required secret); absent/blank key disables Luna, never the whole Worker. Add it to secret redaction. Provision only after explicit human approval; never commit credentials. No existing secret or Cron changes now.
