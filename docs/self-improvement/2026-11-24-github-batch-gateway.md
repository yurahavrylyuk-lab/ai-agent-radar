# GitHub Batch and D1 gateway

Local implementation only. The existing Cloudflare scheduled entry point, configuration, and migration allowlist still control production.

- `src/batchGatewayWorker.ts` accepts POST requests at `/v1/batch` with a dedicated 32-byte random hex bearer secret over HTTPS. A typed operation table delegates to existing D1 stores. Callers supply no SQL, account token, or database identifier. Keep Cloudflare request logs for this gateway free of authorization headers and payloads.
- `src/githubBatchRunner.ts` reuses Worker Batch composition and native provider transports under Node 24. It disables Threads and X. Feedback is optional. The Gemini retry/failover proof, discovery and notification history, email composition, quota stores, and delivery ledger stay authoritative.
- `ops/github-batch.inactive.yml` is outside GitHub's workflow directory. The template uses 08:07 and 09:17 UTC and operator-only same-day recovery from the protected environment. The scheduled runs use a fixed 08:00 UTC delivery identity within a bounded morning window. Keep protection rules for `main`, use trusted maintainers, and pin workflow dependencies before enabling it.

## Admission and recovery

The existing migration 0002 table stores a permanent `github-batch:admit:YYYY-MM-DD` marker. Only the winner of its atomic insert can start providers. A lost insert response holds the day. There is no whole-cycle retry. Fallback starts the Batch only if primary never claimed it. Otherwise fallback and manual recovery share one delivery-only marker, available after 15 minutes and only if a same-day frozen delivery row exists. The workflow times out after 10 minutes. Keep those two timings ordered. Recovery can reconcile accepted evidence or attempt the same frozen payload with its original Resend idempotency key under the existing ledger lease and retry cutoff. Failures before freezing the payload may leave the day without a digest. A committed recovery marker with an unknown response also holds.

This is the single-process Batch path. It omits staged Queue receipts, durable per-source results and continuation, per-Brave-request reservation/arming, and two-minute recovery. The Batch Brave guard uses usage reads and successful-response accounting. One whole-cycle winner plus an exclusive scheduler cutover are required. Any overlapping legacy run would bypass the Actions marker. Keep production legacy active until a separately approved cutover. Stop the legacy schedule and verify no in-flight run before enabling Actions for the next UTC day. Do not reset claims or accepted history to force a run.

### Operator procedure

1. Check the failed run's `github_batch_result` for the UTC logical date, action and bounded reason. A held day, expired schedule or unconfirmed completion exits nonzero. If a job timed out before it could log a result, use its run metadata and inspect the authorized, read-only admission and delivery evidence for that date. Treat lost replies as uncertain.
2. If the day was claimed and the delivery row is absent (`no_frozen_payload`), preserve the claim and provider-accounting evidence. There is no safe way to restart discovery or reconstruct a digest from an interrupted Batch run. Record the missed digest and let the next day's schedule use its own key.
3. If a delivery row exists, and the original job has ended, use **Run workflow** on protected `main` with that exact same-day UTC `logical_date` (`YYYY-MM-DD`). The 15-minute D1 prerequisite, one recovery claim, ledger lease, payload integrity and retry cutoff still apply. If recovery is denied or still uncertain, inspect the ledger read-only. Leave the claim and delivery history intact. A timeout alone does not authorize a send.
4. If neither schedule starts, GitHub cannot emit a runner result. Check the Actions run list for both expected occurrences. With no frozen row, manual recovery cannot start a new Batch. Record the missed day and preserve all authority records.

Each scheduled trigger includes its UTC weekday in the Cron expression. The runner checks that weekday, GitHub's original run `created_at`, and the current UTC time. Primary and fallback use the same date/key and expire at noon UTC. A queued run crossing midnight expires, and a trigger first materialized on a different weekday fails closed. GitHub does not document an exact intended-fire timestamp. A trigger first materialized a full week late (or a multiple of a week) during the matching morning window cannot be distinguished from that week's trigger using these fields. Treat that as an unattended scheduling limitation. `cancel-in-progress: false` protects the running digest, while D1 controls execution and delivery authority.

## Release gates

1. Independently review the code and confirm the required existing tables, including 0002 and 0008–0010, are present. No new migration is part of this change. The gateway example has a placeholder binding and no public route. Provisioning a reachable isolated gateway or configuring the protected GitHub environment requires separate approval.
2. Repeat live CPU and resource measurements for the complete operation set. Include largest frozen payloads, Gemini atomic settlement and quota scans, Luna accounting, bulk history, and max-size ledger alias reconciliation. The gateway caps Brave and Gemini usage reads at 2,048 records each and fails closed on overflow. Verify current counts, growth, and the operational response before enabling; never drop historical ambiguity or silently truncate usage.
3. Provision a dedicated rotatable gateway secret in Cloudflare and GitHub, and use the protected `ai-radar-batch` environment with reviewed `main` only. Add provider secrets and reviewed quota variables there. Enable only after a separately approved cutover. A bearer key is replayable if exposed. Do not share it with CI/PR jobs or put it into logs.
4. Treat delayed or dropped GitHub schedules, an unavailable gateway, and a held logical day as observable failures requiring operator review. Do not use a different logical date or idempotency key to repair an uncertain send.

### Optional feedback activation

With feedback variables and signing secret unset, the runner issues no feedback RPCs and the digest has no feedback links. A separately approved activation requires the existing migration `0011` on the shared D1 database, the approved HTTPS origin on the feedback-serving Worker, and matching active key IDs and signing secrets on that Worker and in the protected GitHub environment. The public confirmation routes continue to use native D1. The Gateway exposes authenticated operations for a bounded aggregate profile, the existing expiration cleanup, and atomic reservation of a frozen digest with up to four article bindings. Vote submission remains on the existing confirmation route.

Verify effective query and body redaction at the feedback origin and applicable log sinks before issuing links. Retest hosted CPU for the profile query, cleanup, and the maximum feedback-bearing frozen reservation. The previously observed 11 ms Gateway operations and frozen-payload storage boundary remain release gates. Retain a single active daily scheduler during any cutover.
